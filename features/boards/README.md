# boards

The spatial view: ideas pinned on a canvas, where an author can see them all at once.

A board holds **placements** — an idea, a spot, a size — and nothing else about the idea. The title an author reads on a card comes from the [idea catalog](../ideas), joined in the client. That is deliberate: a board that stored titles would hold a second copy of a fact it does not own, and every retitle would have to chase it. See [the frontend join](../../ARCHITECTURE.md#the-board-renders-through-a-frontend-join).

**`Board` is an aggregate** — `Started`, `IdeaPinned`, `IdeaMoved`, `IdeaResized`, `IdeaRaised`, `IdeaUnpinned`. Moving and resizing are separate events even though one `Reshape` command can do both, because an event says what changed rather than what a caller asked for. Multiple boards per project are in the model from the first event even though the first version ships one, because keying placements by project id is the shortcut that would turn a second board into a migration of everything ever written.

**A project cannot start its own board**, since a feature may not call another feature. So a board is started on first open — find-or-start, under one write guard — and a project may legitimately have no board yet. Anything sweeping a project has to tolerate that.

**Two projectors and two listeners.** `catalogue-board` keeps the board summaries; `index-pinned-ideas` keeps the index of which boards hold a given idea; `unpin-discarded-idea` hears `idea.discarded` and lays the idea's tombstone; `let-go-of-discarded-idea-everywhere` and `let-go-of-gone-ideas` take a gone idea off the boards, each asked by one of the two before it.

**Heard once, or safe to hear again.** `catalogue-board` is heard through [`inbox::Inboxed`](../../libraries/inbox/README.md): the board's summary and the record of having heard the message commit in one transaction, and a hearing-forgetting chore `forget-old-board-hearings` clears the record after the tombstones' time. So are `index-pinned-ideas`, `unpin-discarded-idea`, `let-go-of-discarded-idea-everywhere` and `let-go-of-gone-ideas`; only the sweep `discard-boards-of-deleted-project` stays a plain listener. **A deleted project opens no board.** `boards-remember-deleted-projects`, heard through the inbox, lays the project's tombstone in the catalog, `project_tombstones`, and asks in the same transaction for the sweep, `follow-up.board.sweep-project`, which `discard-boards-of-deleted-project` hears instead of `project.deleted`, so it reads the registry only once the tombstone has committed. `open` refuses a project with a tombstone as not there, and asks again after its own claim has committed, discarding what it started if the tombstone came meanwhile: of an open and a deletion racing, either the open sees the tombstone or the sweep sees the board. The sweep takes a board not there, or discarded already, as nothing to do; the chore that forgets the other tombstones forgets the projects' too. **A pin racing its idea's discard is still let go of, by a follow-up.** The index of a board's pins and the idea's tombstone are written by two hearings that may run at once, and each must see what the other committed; read in its own transaction, either could miss the other. So each writes and, in the same transaction, puts a follow-up in the outbox, which goes out only once that transaction has committed: `unpin-discarded-idea` asks `follow-up.board.let-go-everywhere` of `let-go-of-discarded-idea-everywhere`, which unpins the idea from every board the index says holds it, and `index-pinned-ideas` asks `follow-up.board.let-go-gone` of `let-go-of-gone-ideas`, which unpins the first idea the board still holds that has a tombstone. Of two racing writers, the later one's follow-up reads the earlier one's commit. The follow-ups' routing keys begin with `follow-up.`, so no `board.#` subscription hears them, and live in the messaging adapter, not the contract, each in the file of the listener that asks it and the one that answers, beside the function that builds it, so a hearing that asks reads as writing and then `outbox.enqueue_within` of that message. A board lets go of one gone idea a hearing, since two unpins on one board in one transaction would collide; the unpin's own `board.idea.unpinned` is heard by the index, which asks the board again, until none is left. Every step is one transaction, the hearing's, and each is idempotent: an idea not pinned or a board discarded is no failure.

**A board is there only for those in its project.** Opening a project's board, reading it and following it live ask the [`Authorizer`](../../libraries/authorizing) for `Read`; pinning, moving, resizing and unpinning for `Write`, an author's. The service reads the board first and asks about its project. Whoever may not read the project is answered 404, as for one not there, and the live route too, before it upgrades; whoever may read but not write is told, 403 `not-an-author`. A reader opening a project's board before anyone has starts it, as opening always has. What the feature does itself, as `Agent::System`, is let through by the authorizer.

**A discarded idea leaves a tombstone.** `idea_tombstones` keeps every idea heard discarded, so a pin indexed after the discard is still let go of, and keeps `laid_at`, the `occurred_at` of the discard. The chore `forget-old-board-tombstones`, a [`ForgetOldTombstones`](../../libraries/chores), forgets it once no message about the idea can still arrive, in batches. A pin of an idea discarded longer ago than that, from a stale or forged request, is no longer let go of; the board keeps it, and the client, which draws only ideas it knows, does not show it.

**A board pins only ideas of its own project.** `boards-remember-projects-of-ideas` hears `idea.captured` and keeps the idea's project in the [`belonging`](../../libraries/belonging/README.md) store, and `unpin-discarded-idea` forgets it as it lays the tombstone, so nothing of a deleted project's ideas stays. `pin` refuses an idea known to be of another project as not there, 404 `not-found`, which it is not for this board, telling nothing of it; an idea not heard of yet is pinned, since a board pins an idea it captured a moment ago, before the capture reaches it (*13c-2b, 2026-11-11*).

**A board forgotten stays forgotten.** The catalog forgets a board discarded by laying a tombstone in `board_tombstones` and deleting its summary in one transaction, and `remember` refuses a board with a tombstone, so a summary heard late cannot bring it back; on PostgreSQL a remember that read no tombstone before a forget committed one loses the race, both transactions being serializable, and is tried again, finding the tombstone (*the lock gone 2026-11-04, every PostgreSQL transaction serializable*, the lock on the board before), and on SQLite the one writer at a time keeps them apart. `forget-old-board-tombstones` forgets them beside the idea tombstones. A summary carries only the board and its project, which never changes, so it needs no version guard.

**Core owns each write's transaction.** `BoardsCore` begins every write's transaction after asking permission; a change runs through `transacting::retrying!`, five tries after a lost race when it names no version and one when it does, `eventsourcing::tries_for(expected)`, so that conflict is answered, a 412; the system's own changes name none. Opening claims the board and starts it in one transaction, so a claim never points at nothing. Cataloguing, keeping what a board holds, laying a tombstone and forgetting old ones each begin one, the catalog's writes taking it.

**One way in: `BoardsCore`.** Opening, reading, following, pinning, reshaping and unpinning, and what the feature does itself, cataloguing, keeping the record of which board holds which idea, letting go of a discarded idea and the sweep after a project is deleted, all go through one struct. It asks `Read` or `Write` of the board's project, and the system's own work is done, and recorded, as `Agent::System`. Only the sweep discards a board. A write answers with the board as written. `BoardService` only carries out the commands, in the transaction `BoardsCore` hands it, and nothing outside the core reaches it. Errors are one enum, `BoardsError`.

**Crates:** `core` (`BoardsCore`, aggregate, catalog port, service, `Spot`/`Size`) · `contract` · `adapters/store` · `adapters/catalog` · `adapters/messaging` (event publisher, catalog projector, discard listener) · `adapters/rest` · `wiring` · `tests`.
