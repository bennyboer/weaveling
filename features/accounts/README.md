# accounts

Who someone is on a Weaveling server: signing up, signing in, and the operator who looks after the instance.

Only a server with `WEAVELING_ACCOUNTS=on` has accounts. Local mode has none, and everything is done by the one person at the keyboard, `Agent::Local`; nothing in this feature runs there.

**`Account` is an aggregate**, event-sourced as every feature is: `SignedUp`, `SignedUpByInvitation` (its address confirmed from the start, since the link reached it), `EmailVerified`, `PasswordReset`, `BecameOperator`, `StoppedBeingOperator`, `Locked`, `Unlocked`. Its events say *that* a password was set or reset, never the password; **a sign-up is published with the name and address under `personal`**, for members to show whom they list, and nothing else personal is ever published; **the secrets are kept beside the events**, latest only, so an old log holds no old hash. Beside them stand the address an account holds, its password's Argon2id hash, the pending codes, the sessions (by the digest of their token), the tries counted by [`throttling`](../../libraries/throttling) who is appointed an operator, and the tickets for invitations (by the digest of the link's token, with the address invited, until when, the project it invites into if any, and whether an operator issued it), each behind a port of its own in `SecretStores`. A ticket is found by its link's digest, or, for an account taking it up in the application, by its invitation (`digest_of_ticket`, while it is still open), and is taken once, and ends when taken or when its invitation is withdrawn; an ended ticket stays ended, so an issue told again, as messages may be, opens no link that was closed. Once its invitation retires, `invitation.retired`, the ticket goes altogether, open, ended or a mark; invitations retire none before it runs out, so nothing told after can make a ticket that still opens. The tickets come from the invitations' messages, by the listener `keep-invitation-tickets`, so accounts never ask invitations anything; it forgets a ticket when its invitation is withdrawn or declined, the latter for one turned down by its link without an account, which accounts would not otherwise hear of. An invitation to an address that has an account already is declined by that account, `InvitationDeclined` with a `DeclineReason` (`AddressHasAccount` here, `TurnedDown` below), told as `account.invitation.declined` with the invitation and the reason, `address-has-account`, and keeps no ticket. That is so for an invitation to the instance alone: an invitation into a project keeps its ticket whoever the address belongs to, since an account takes it up signed in. Signing up through an invitation into a project works as through one to the instance, and takes it up alike; where signing up is by invitation only, only an operator's invitation signs anyone up, so one from a project's owner is refused with `InvitationNotByAnOperator` (403 `invitation-not-by-an-operator`) and left for its address. An address with an account already is told to sign in before any ticket is used, so the link still works signed in. **An account takes an invitation up** with its link while signed in (`take_up_invitation`): only an invitation into a project, an invitation to the instance being for signing up alone, and only one sent to the account's own address, refused otherwise with `InvitationForAnotherAddress` naming the address it was sent to and left for it, and only until it runs out. The ticket is used up and the account records `InvitationTakenUp`, told as `account.invitation.taken.up`, the account itself its agent. Signing up through an invitation records `InvitationTakenUp` too, right after `SignedUpByInvitation`, so every invitation an account took up shows alike in its history; `SignedUpByInvitation` itself names no invitation, which is told once, as taken up. `POST /accounts/current/invitations/accept` with the link's token takes one up for whoever is signed in, answering 204; one sent to another address is refused 403 `invitation-for-another-address`, the problem naming the address in `to`, so the page can offer to sign in as it. `POST /accounts/current/invitations/{invitation}/accept` takes one up by its id, for an account told of it in the application, under the same checks, but one sent to another address is refused as `invitation-invalid`, as though not there: an id may be guessed where a link may not, so whom it went to is not told. **Turning one down** goes through the same checks, save that any invitation may be turned down, the instance's too, where only a project's is taken up, and uses the ticket up the same way: `POST /accounts/current/invitations/decline` with the link's token, or `POST /accounts/current/invitations/{invitation}/decline` by its id, answering 204; the account records `InvitationDeclined` for `turned-down`, itself its agent, told as `account.invitation.declined`, and invitations mark it declined, as they do one declined because the address has an account already.

**An address is claimed in the transaction that begins its account,** so two sign-ups never share it, and the claim, the account's first events and its password land together or not at all; signing up by invitation takes the ticket in that same transaction. A claim keeps when it was made, and one whose holder never came to be an account is taken over by the next sign-up once five minutes have passed, which only a claim left from before the two were one transaction still needs.

**A password reset is one transaction too:** its event, which ends the sessions begun before it and confirms the address, and the new password land together. A reset whose new password cannot be kept changes nothing, the old password still standing, and the same code finishes it; ending the sessions while the old password still let its holder back in protected nothing, which is why it is no longer told first.

**Signing up is open or by invitation** (`SigningUp`, set by the server from `WEAVELING_SIGN_UP`). By invitation, a plain sign-up is refused and the link is the only way in, but for the first: while nobody is an operator, a sign-up bringing the operator code from the server's log is let in, and the code, only looked at then, makes that account the operator once its address is confirmed; `/api/service/mode` tells `operator_wanted` meanwhile; `POST /accounts/by-invitation` takes its token, a name and a password, makes the account confirmed and opens its session at once, answering as signing in does, since whoever followed the link need not know the address it came to.

**An invitation's ticket goes with what it lets in.** The invitations feature tells accounts of each invitation it issues, and accounts keeps a ticket for it, its token kept by digest. Taking an invitation up or turning it down takes the ticket and appends to the account in one [transaction](../../libraries/transacting/README.md), so an append that fails leaves the ticket to be used again; keeping a ticket for an address that already has an account forgets it and declines for that account in the same transaction, so a decline that failed is made again when the issue is told again. The ticket store's writes take that transaction; its reads do not.

**Sessions end by comparison, not by sweeping.** An account records when its sessions last stopped counting, `sessions_since`, set by a new password or a lock; a session begun before that is over wherever it is kept. *A session is dated from when signing in began (2026-11-02):* `begun` is taken before the password is read and checked, not once Argon2 has said yes, so a reset landing while the old password is being checked dates the session before it, and the session is over as the others are. A locked account is admitted with no session at all.

**Nothing tells a stranger whether an address has an account.** Signing in with an address nobody has does the same Argon2 work and is refused in the same words; signing up with a taken address is answered as any sign-up, and its owner gets a mail; throttles count per address whether or not one stands behind it. A locked account hears so only once its password is right.

**The operator** is whoever entered the code the server logs at start while there is none; an operator may make other accounts operators, the last one always kept, and lists, locks and unlocks accounts. See [the instance](../../ROADMAP.md#milestone-17--accounts-members-and-roles) in the roadmap for the rest of slice 3.

**An invitation into a project in the trash waits.** *2026-11-02, slice 6d:* the listener `accounts-remember-trashed-projects`, heard through [`inbox::Inboxed`](../../libraries/inbox/README.md), hears `project.trashed`, `project.restored` and `project.deleted` and keeps in the accounts catalog, by the project's version and only ever forward, whether a project is in the trash (`remember_trash`, `forget_trash`, `is_in_the_trash`, in `trashed_projects` on PostgreSQL and SQLite; *kept beside the invitation tickets until 2026-11-10, moved to the catalog at the user's asking, as a read model of another feature's messages, as the projects' members are*), forgetting its row whole once it is deleted, as members do. Taking up an invitation into a project, by its link or its id, and signing up by one, ask in their transaction, before the ticket is taken, whether its project is in the trash, and refuse it as `InvitationPaused`, 409 `invitation-paused`, the ticket left as it was, so the invitation is good again once the project is restored; turning one down stays open, and an invitation into the instance is in no trash. The sweep after the purge withdraws it as before. Accounts decide it, not invitations or members, as taking up appends to the account before either hears of it.

**Deleting an account waits thirty days.** *Slice 9, 2026-11-09:* the holder asks for it with the password (`ask_deletion`), or the operator marks another account (`mark_for_deletion`); the account is then `PendingDeletion` until a day thirty days on (`KEPT_BEFORE_DELETION`), every session ended and signing in refused as locked, an operator dismissed in the same step unless the last, refused as `LastOperator`, the role not coming back if the account is kept. Signing in to such an account is not refused: once the password and the second step are answered, the session opens at `Stage::DeletionPending`, which acts on nothing and only keeps the account or signs out. The holder keeps an account they asked to delete from that session (`keep_account`), going on signed in under a new token, the operator any (`keep_account_of`); what the operator asked, only the operator calls off (`DeletionAskedByTheOperator`). Both are refused while the account is the last owner of a project others are in, `ProjectsToHandOver` naming them, a project in the trash left out. Accounts learn who is in which project from the members' own messages, never by asking them: the listener `remember-project-members` hears `members.founded`, `joined`, `role.changed`, `left`, `removed` and `disbanded`, and the catalog keeps what each account is in each project, owner or member, by the members' version for each account (`remember_holding`, `remember_disbanded`, `projects_to_hand_over`, tables `project_holdings` and `disbanded_projects`), a member gone kept as gone, so a change heard late, as a retried delivery may be, never undoes a newer one. **The guards are forgotten once nothing can come late:** a member gone keeps when (`gone_at`) and a project disbanded when (`laid_at`), and the chore `forget-old-account-tombstones`, `ForgetOldTombstones` over `AccountsCore::forget_tombstones_laid_before`, forgets those laid `TOMBSTONES_KEPT_FOR` ago, a disbanded project with everything held in it. Eventually consistent: an owner made a moment ago may not count yet, which the sweep makes up for (slice 9d). Asking puts the account into the accounts' own trash (`libraries/trash`) until its day, keeping takes it out, and the hourly chore `sweep-deleted-accounts` sweeps those whose day has come (`AccountsCore::sweep`): the account is `Deleted` as the system, holding neither name nor address afterwards (`deleted@account.invalid`, "Deleted"), refusing every command (`Gone`), and compacted at once, a snapshot of it gone and every earlier event pruned, so only its id remains; in the same transaction its address is released, free to sign up anew, and every secret store forgets the account whole: its password, its sessions at any stage, its codes, its second step and its keys' credentials (`forget_password_of`, `end_every_session_of`, `forget_codes_of`, `forget_second_factors_of`, `forget_credentials_of`). The catalog forgets it whole on hearing `account.deleted`. The events are published, `account.deletion.asked` with its day and who asked, `account.deletion.called.off`, for the members to freeze the account's roles and, later, for the sweep. **Over REST** (*9e-1, 2026-11-10*): `POST /accounts/current/deletion` with the password asks for one's own account to be deleted, answering `DeletionDTO { until, by }` and letting the cookie go, as every session of the account ended; asked again it answers the day first asked, as `ask_deletion` and `mark_for_deletion` answer the `PendingDeletion` that stands. `DELETE /accounts/current/deletion` keeps it, from the session signing in opened while it is pending, which the routes behind signing in turn away, so it sits on the open router and reads the cookie itself, as the second step's routes do; it answers `SignedInDTO` under a new cookie. `GET /sessions/current` tells `deletion` while one is pending. Refused as `password-wrong`, `projects-to-hand-over` with the `projects`, `last-operator`, `no-deletion-pending` and `deletion-asked-by-the-operator`, worded in all five languages. The operator marks another account with `PUT /instance/accounts/{account}/deletion`, answering `DeletionDTO`, and calls off any deletion with `DELETE` on the same path, `204`, also where none is pending, as calling off nothing changes nothing; both take `If-Match` as the operator's other acts do, refused as `outdated` from a version the account moved past, and an account swept is not found. The operators' list tells each account's pending deletion, `AccountSummaryDTO.deletion`, kept in the catalog as `deletion_until` and `deletion_asked_by` (*9e-2, 2026-11-10*).

**Core owns each write's transaction.** `AccountsCore` begins every transaction from the feature's `Transactions`: signing up claims the address, begins the account and keeps the password in one, the Argon2 hash and the throttle before it and the mail after; every command on an account that is already there runs through `transacting::retrying!`, five tries after a lost race, none naming a version, taking up or turning down an invitation trying again the ticket's take with it, so a ticket taken in a lost try is given back; the list's `remember` takes it too. A transaction that fails is `AccountsError::Transaction`, no longer passed off as the secrets' error. Its listeners, `catalogue-account` and `keep-invitation-tickets`, are heard through [`inbox::Inboxed`](../../libraries/inbox/README.md), which begins the transaction, records the message as heard in it and finishes it, a lost race left for the delivery to offer the message again; cataloguing and keeping, forgetting or dropping a ticket join it, so keeping a ticket for an address with an account declines for that account in the same transaction as the hearing, and a decline that failed leaves the message unheard, to be taken in anew. `forget-old-account-hearings` forgets the hearings of old; `AssembledAccounts` hands it out as `chores`. Verifying closes its code, and resetting a password keeps the new one and closes its code, in the transaction of their event; a try at a code is counted in a transaction of its own first, so a failure after it never gives the try back. *Closing takes the code, 2026-11-02:* `close` deletes the pending code only if it is still the one checked, and says whether it did, first thing in the writing transaction, so two resets or confirmations with one code that both got past the check use it once, the second refused as a wrong code, and a code sent anew meanwhile is not closed by the old one. Becoming, being appointed and being dismissed write the event and the operators' table in one, the operator code taken in it, so operator status cannot drift between the two. Sessions open and end, and codes are issued, each in one of their own.

**One way in: `AccountsCore`.** Signing up, verifying, signing in and out, resetting a password, becoming an operator and cataloguing all go through one struct. Locking, unlocking, listing, appointing and dismissing ask whether the agent is an operator, there and nowhere else. The struct does the work itself, its use cases kept in one file each under `core/src/accounts/`, signing up, invitations, codes, sessions and operating, as `impl` blocks of the same struct, and what they share in `accounts.rs`; there is no service behind it, so whoever reads a use case sees the whole of it. Errors are one enum, `AccountsError`.

**Crates:** `core` (`AccountsCore`, aggregate, secret stores, catalog port, service, tokens and codes) · `contract` (DTOs, refusals and routing keys, shared with the client) · `adapters/store` (stored-event codec) · `adapters/secrets` (the secret stores in memory, on PostgreSQL and on SQLite) · `adapters/catalog` (the list of accounts) · `adapters/messaging` (event publisher, catalog projector) · `adapters/rest` (routes, the gate, the cookie) · `wiring` · `tests`.
