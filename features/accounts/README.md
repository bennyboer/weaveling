# accounts

Who someone is on a Weaveling server: signing up, signing in, and the operator who looks after the instance.

Only a server with `WEAVELING_ACCOUNTS=on` has accounts. Local mode has none, and everything is done by the one person at the keyboard, `Agent::Local`; nothing in this feature runs there.

**`Account` is an aggregate**, event-sourced as every feature is: `SignedUp`, `SignedUpByInvitation` (its address confirmed from the start, since the link reached it), `EmailVerified`, `PasswordReset`, `BecameOperator`, `StoppedBeingOperator`, `Locked`, `Unlocked`. Its events say *that* a password was set or reset, never the password; **the secrets are kept beside the events**, latest only, so an old log holds no old hash. Beside them stand the address an account holds, its password's Argon2id hash, the pending codes, the sessions (by the digest of their token), the tries counted by [`throttling`](../../libraries/throttling) who is appointed an operator, and the tickets for invitations (by the digest of the link's token, with the address invited, until when, the project it invites into if any, and whether an operator issued it), each behind a port of its own in `SecretStores`. A ticket is taken once, and ends when taken or when its invitation is withdrawn; an ended ticket stays ended, so an issue told again, as messages may be, opens no link that was closed. Once its invitation retires, `invitation.retired`, the ticket goes altogether, open, ended or a mark; invitations retire none before it runs out, so nothing told after can make a ticket that still opens. The tickets come from the invitations' messages, by the listener `keep-invitation-tickets`, so accounts never ask invitations anything. An invitation to an address that has an account already is declined by that account, `InvitationDeclined` with a `DeclineReason` (so far only `AddressHasAccount`), told as `account.invitation.declined` with the invitation and the reason, `address-has-account`, and keeps no ticket. That is so for an invitation to the instance alone: an invitation into a project keeps its ticket whoever the address belongs to, since an account takes it up signed in, and signing up through one is refused for now, the ticket left for its address. **An account takes an invitation up** with its link while signed in (`take_up_invitation`): only an invitation into a project, an invitation to the instance being for signing up alone, and only one sent to the account's own address, refused otherwise with `InvitationForAnotherAddress` naming the address it was sent to and left for it, and only until it runs out. The ticket is used up and the account records `InvitationTakenUp`, told as `account.invitation.taken.up`, the account itself its agent. Signing up through an invitation records `InvitationTakenUp` too, right after `SignedUpByInvitation`, so every invitation an account took up shows alike in its history.

**An address is claimed before its account is begun,** so two sign-ups never share it; a claim keeps when it was made, and one whose holder never came to be an account is taken over by the next sign-up once five minutes have passed, so a server stopping between the two steps does not keep the address from anyone for good.

**Signing up is open or by invitation** (`SigningUp`, set by the server from `WEAVELING_SIGN_UP`). By invitation, a plain sign-up is refused and the link is the only way in, but for the first: while nobody is an operator, a sign-up bringing the operator code from the server's log is let in, and the code, only looked at then, makes that account the operator once its address is confirmed; `/api/service/mode` tells `operator_wanted` meanwhile; `POST /accounts/by-invitation` takes its token, a name and a password, makes the account confirmed and opens its session at once, answering as signing in does, since whoever followed the link need not know the address it came to.

**Sessions end by comparison, not by sweeping.** An account records when its sessions last stopped counting, `sessions_since`, set by a new password or a lock; a session begun before that is over wherever it is kept. A locked account is admitted with no session at all.

**Nothing tells a stranger whether an address has an account.** Signing in with an address nobody has does the same Argon2 work and is refused in the same words; signing up with a taken address is answered as any sign-up, and its owner gets a mail; throttles count per address whether or not one stands behind it. A locked account hears so only once its password is right.

**The operator** is whoever entered the code the server logs at start while there is none; an operator may make other accounts operators, the last one always kept, and lists, locks and unlocks accounts. See [the instance](../../ROADMAP.md#milestone-17--accounts-members-and-roles) in the roadmap for the rest of slice 3.

**One way in: `AccountsCore`.** Signing up, verifying, signing in and out, resetting a password, becoming an operator and cataloguing all go through one struct. Locking, unlocking, listing, appointing and dismissing ask whether the agent is an operator, there and nowhere else. `AccountService` does the work, and nothing outside the core reaches it. Errors are one enum, `AccountsError`.

**Crates:** `core` (`AccountsCore`, aggregate, secret stores, catalog port, service, tokens and codes) · `contract` (DTOs, refusals and routing keys, shared with the client) · `adapters/store` (stored-event codec) · `adapters/secrets` (the secret stores in memory, on PostgreSQL and on SQLite) · `adapters/catalog` (the list of accounts) · `adapters/messaging` (event publisher, catalog projector) · `adapters/rest` (routes, the gate, the cookie) · `wiring` · `tests`.
