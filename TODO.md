- [x] ~~**A key right after typing was sometimes lost.**~~ **Fixed 2026-10-14.** *A word jump inside a scene stays a word jump* and *moving up inside a scene stays in it* failed 2–5 times in 100 parallel runs: an arrow key or word jump moved the caret, and the next words still landed where it had been. Found by recording keys, selection changes and transactions in the page, then timers. When an editor gains focus, ProseMirror schedules a check 20ms later that puts its own selection back if the browser's differs. Under load that timer fired late, between the browser moving the caret for the key and ProseMirror hearing of it, and undid the move. Our editors already let the browser's selection win everywhere else, so the editor now takes focus the way ProseMirror does, minus that write-back. It fails 8 times in 10 without the fix, and the two flaky tests passed 300 runs under load with it.
- [x] ~~**Moving the cursor right after typing was undone.**~~ **Fixed 2026-10-12 — two causes, both in how ProseMirror learns where the browser's cursor is.** (1) The browser moves the cursor at once on Home, End or an arrow but tells ProseMirror only on the next `selectionchange`, so a key command arriving in between — Enter above all — acted on the old position, and an editor update in between wrote the old position back. The editor now brings its selection up to date with the browser's before any key command, and an update that sets no selection of its own takes the browser's rather than restoring a stale one. This was in every scene editor since M6; 3c's Enter only made it visible. (2) Within 200ms of the editor receiving focus not by click or touch, desktop Chrome's ProseMirror treats a cursor at the very start of the document as the browser resetting the caret and puts its own selection back — so Home right after crossing into a scene was undone. Crossing now clears that just-focused mark, since the move is ours. The second relies on ProseMirror's internal `input.lastFocus`; *a word jump at a scene's edge carries on into the next scene* fails without it. Found by measuring rather than guessing: a probe on both pages in both modes, then the editor recording keys, transactions and selection changes into the page, read only after a failure.

## Carried out of the Phase 2 spikes

Real gaps found while spiking, to settle when prose becomes production code rather than a spike.

- [ ] **Awareness tombstones on disconnect.** The sync server treats awareness as opaque bytes, which is the right default — but it means it cannot retract a departed peer's cursor, so stale cursors linger until the client-side timeout (~30 s). Fix: decode just the awareness header (client id, clock, state), remember which ids a connection spoke for, and broadcast a null state when it drops.
- [ ] **A change to the outline costs in proportion to the book.** Found by the M13c slice 6 stress test (2026-10-14): attaching 10,000 scenes took 35 minutes, the last thousand ten times slower than the first. Each change loads the newest snapshot, which holds every section and every attachment, writes a whole-book snapshot every 100 events, answers with the whole outline, and the listeners that index it load it again. At 10,000 scenes a new scene or section in the writing view costs about half a second on the server and around 600 KB to the browser. Options: snapshots that do not grow with the book, answers carrying only what changed, listeners reading the event instead of reloading. **Measured 2026-10-15 (P1)** with `cost_per_change` in `features/outline/tests`, an ignored test run on purpose, which grows one outline on memory and SQLite and times one change at 1,000, 2,500 and 5,000 scenes. At 5,000 on SQLite, debug build as the stress servers run: loading the outline 8.7 ms (the snapshot read 4.9 ms of it), an attach through the service 19 ms, slowest of 100 with a snapshot due 30 ms, an attach through REST with its answer 34 ms, and **the `index-attachments` listener 142 ms, 131 ms of it rewriting the attachment index**: it deletes every row of the outline and inserts every attachment again, one statement each, in one write transaction. Release builds are three to five times faster throughout, the listener 92 ms. On memory nothing passes 9 ms. The answer is 229 KB. So snapshots and loading are not the problem yet; the index rewrite is, and it holds the outline database's write lock for over 100 ms on every change, which the outbox and the event store have to wait behind. That is likely part of the stalls below. **P2 done:** the listener still indexes from the latest outline, so the order messages arrive in still cannot matter, but on SQLite `holds` now reads the rows the outline has and writes only the difference, in an immediate transaction so the read cannot go stale before the write. At 5,000 the listener takes 30 ms instead of 142, and its write lock covers one read and a row or two instead of 5,000 inserts; PostgreSQL already wrote the whole set in one statement. What is left of a change is loading the outline in the listener and in the answer, and the 229 KB answer itself. **P3 done:** a write answers with every section's place and title but sends attachments only for the sections whose attachments the change touched, read from the `Attached` and `Detached` events that landed; if another write landed in between, every section's attachments go, as before. Both views lay the change over the outline they hold, keeping the attachments of sections it did not send, so no rule of the outline is repeated in the browser. Opening still sends the whole outline. With chapters of 50, the bench answers 10 KB at 5,000 scenes where it answered 229 KB; it grows with the sections, not the scenes. Left, and not pressing at 5,000: a REST write loads the outline twice, once to change it and once to answer, 34 ms in all on SQLite in a debug build. This entry can close once the 10,000-scene book seeds in reasonable time.

- [ ] **"All saved" trusts the store.** The writing view's note counts a scene saved once the server answers a question asked after the edit (M13c 4a). - [x] ~~**Compaction has to actually run.**~~ *Resolved: the PostgreSQL store writes a snapshot and forgets what it covers once 64 updates pile up behind the last one (`COMPACT_AFTER`), and the in-memory store only ever keeps the merged state. Eviction no longer needs to compact.* The original note: Measured: an append-only log is 11–13× the compacted form after 500 rewrites of one paragraph. `Y.mergeUpdates` is lossless so this is safe, but nothing schedules it yet. Natural trigger: eviction (below), so a scene is compacted on its way out of memory.
- [x] ~~**Live scenes are never evicted.**~~ *Resolved in [M13 step 0a](./ROADMAP.md#milestone-13--local-mode), in the intended shape: `join` hands out a `Presence` that counts in and out under the map's write lock, and a sweeper lets go of a scene nobody has been in for 30 seconds. No flush is needed in the normal case, because every edit is stored before the next frame is read; a scene whose edit the store refused is flushed whole first, and stays live while that keeps failing. The multi-instance version below is still open.* The original note: `LiveScenes::hydrate` inserts into the `Hydrated` map and *nothing ever removes*. On disconnect `stay()` aborts its tasks and drops its channel; the map is untouched. So a scene stays in memory for the process lifetime whether anyone is connected or not — bounded by the number of distinct scenes ever opened, which for a book of thousands of nodes eventually means all of them, at roughly 10 KB of document each. [Local mode](./ARCHITECTURE.md#two-ways-to-run-it) makes this bite: a process that lives as long as the author's afternoon has no restart to save it.

  **Not a two-line fix.** Refcounting participants and dropping at zero has a real hazard:

  ```
  peer A disconnects  -> count hits 0 -> entry removed from the map
  peer B, meanwhile, is mid-hydrate and already holds the Arc
  peer C joins        -> map is empty -> hydrates a SECOND copy from the store
  ```

  Two live copies of one scene now exist, and two authors are silently invisible to each other until both persist and someone rehydrates. Worse than the leak. Two related traps: persistence happens *after* relay, so eviction must flush or it discards a relayed-but-unpersisted update; and `Arc::strong_count` looks tempting but is not a synchronisation point.

  **Intended shape:** count participants inside the map's write lock (so `hydrate` cannot interleave with a decrement-to-zero), and have a background sweeper remove entries idle for a grace period (~30 s) — the grace period is what turns the race above into a non-event, since a rejoin inside the window finds the existing entry. A guard returned by `hydrate` that decrements on `Drop` is the more idiomatic way to count (impossible to forget, survives a panic in `stay()`), but it cannot replace the sweeper: `Drop` is not async and eviction needs to await a final persist. So `Drop` marks, the sweeper collects and compacts.

  **The permanent version of the same problem:** across two server instances both can hydrate the same scene, and no amount of eviction or grace period helps. Same failure the snapshot-vs-log `apply` analysis turned up. Single-instance eviction is tidy-up; multi-instance needs sticky routing by scene id or a shared coordination layer.

- [ ] **Dead letters are collected but never retried.** *Mostly resolved in M11b: a refused message is retried up to five times and then dead-lettered into a durable table. Still owed is the last part below — surfacing the pile to a human — which is [M13 step 7](./ROADMAP.md#milestone-13--local-mode). The original note:* `InProcessDispatcher` hands a refused message to a `DeadLetters` sink, and the default sink logs it. That is the whole story today: nothing retries, nothing reports, and a projector that fails leaves its read model wrong until the process restarts — and in [local mode](./ARCHITECTURE.md#two-ways-to-run-it) there is no restart to wait for and no ops staff to read the pile, which is why that mode wants a strict dispatcher that surfaces the refusal to the author instead. The shape is deliberate — a **publisher must never learn listener outcomes**, because over a broker it cannot: publisher confirms say the *broker* accepted the message, `mandatory` plus `basic.return` says it reached no queue at all, and consumer acks go to the broker rather than back to the publisher. Anything richer would be an in-process-only guarantee that vanishes the day RabbitMQ arrives. **What is still owed:** retry with backoff, a durable dead-letter store, and something that surfaces the pile to a human. The reference implementation pairs every listener with a dead-message handler, which is the shape to copy.
- [x] *Resolved 2026-11-02: every kept listener but the sweeps is heard through its inbox, and a `Handler` must say why it has none.* **Nothing forces a listener to be idempotent yet.** `InProcessDispatcher` delivers each message exactly once, synchronously and in order; **RabbitMQ delivers at least once** — on nack, on a dropped connection, on a consumer restart. So every listener written between now and a broker will pass its tests and be quietly wrong, and the failure will arrive all at once, in production, in whichever projector was least defensive.

  This is the [publisher-side mistake pointing the other way](./ARCHITECTURE.md#at-least-once-is-the-trap-this-design-has-to-survive): there the in-process adapter could promise *more* than a broker, here it promises *less*, and the same rule settles both — the port may promise only what either transport can keep.

  **Intended shape:** an inbox that dedupes on `(listener name, message id)` inside the same transaction as the handler, which is why `ListenerName` exists now rather than later — the reference implementation keys its inbox `name + messageId`, making idempotency per listener rather than global. It needs a transaction to be worth anything, so it lands with the real store. **What can land sooner and should:** a dispatcher that redelivers on purpose in tests, so a listener that is not idempotent fails while it is cheap to fix. `Delivery::Fleeting` listeners are exempt — a redelivery they miss is one they were always allowed to miss.

- [ ] **A redelivered sweep forks into two chains, and an inbox would not notice.** *Noted 2026-10-29.* The ideas and scenes sweeps take a page and publish `MORE_TO_SWEEP` for the next one. If the handler publishes and then dies before the ack, the broker hands the same message over again: the page is already discarded, so that part is a no-op, but a *second* continuation goes out. `Message::answering` mints a fresh `MessageId::generate(now)` each time, so the two continuations are different messages, and an inbox keyed on `(listener name, message id)` lets both through. From then on two chains walk the project side by side. They converge, because every discard treats `Discarded` or `NotFound` as success and two discards racing on one idea are settled by the version check, so nothing is wrong; only the work doubles, once for every unlucky redelivery.

  **The inbox cannot be the guarantee here.** It is only worth something inside the handler's transaction, and a sweep page is N aggregates, each in a transaction of its own, followed by a publish in none of them. What actually protects a sweep is that each discard is idempotent; the inbox could only spare it repeated work.

  **Intended shape:** a continuation's id derived from what it continues: a UUID v5 over `(listener name, project, after)` rather than one generated. Both forks then publish the *same* id, and the inbox collapses them for free once it exists. Scenes' restyling needs it too: `tasks.claim` passes on `latest_change <= excluded`, so a redelivered page of the *same* change claims again and forks.

- [ ] **A projection cannot be rebuilt wholesale, because `EventStore` cannot be enumerated.** Every method takes an `AggregateId` — `read_from`, `read_through`, `latest_snapshot`, `snapshot_at_or_before`, `prune_through` — so there is no way to ask for "every idea stream".

  **This is smaller than it first looks, and the first write-up of it overstated the case twice.** Repairing *known* drift needs no enumeration: because the [projector re-reads state and is idempotent](./ARCHITECTURE.md#the-first-consumer-the-idea-catalog-as-a-projection), fixing one dropped message is re-cataloguing that one idea. And [local mode](./ARCHITECTURE.md#two-ways-to-run-it) does not need it either — the export holds every aggregate's event stream, so the *importer* carries the enumeration and can feed each stream through the projector as it reads it. The port stays out of it.

  **What actually needs it** is rebuilding against a store nobody just imported, and the routine case is the strongest one: **an event gets patched**, or the *summary* gains a field. Both are ordinary evolution rather than a fault, and both leave existing rows quietly stale with nothing to announce it. The alternative — migrating the catalog table in SQL — means writing the events-to-summary derivation a second time, in a second language, where it can drift from the projector that owns it. When the new field comes from event metadata rather than the old row, a migration cannot produce it at all.

  Two narrower cases sit behind that: a projector bug, where the code is fixed and every existing read model is now wrong; and a new projection over existing history, which the board and the outline both are. None of it can bite while nothing is durable.

  **Patching is narrower here than it looks**, because the projector reads through `events.latest`, which applies the patcher — so an idea that is touched again after a patch lands re-catalogues itself correctly. The exposure is ideas nobody touches again, which in a book is most of them.

  **So the shape is deliberately undecided.** A streaming port method is one answer, and if it is chosen it must be a stream rather than a `Vec`, since a rebuild reads everything. But a real database can scan or tail a change stream natively, and if messages are durable then replay belongs to the message log rather than the store — which would put this behind the outbox instead. **Trigger:** M11, and decide it against the store that actually gets picked.

Both now **mark the attachment gone first** (`gone_attachments`, the outline catalog's version of appearances' tombstones) and then detach what the index shows. `index-attachments`, after writing what an outline holds, detaches whatever of it is gone. Each side writes before it reads, so at least one of them sees the other. The cost is that one projector now issues a command, which blurs the split above on purpose.

- [x] ~~**The board should hear about discarded pieces and unpin them.**~~ Built. `unpin-discarded-piece` listens on `piece.discarded` and takes the piece off every board holding it, and it stays **housekeeping rather than correctness** — the client must keep tolerating dangles, because a broker always leaves a window and the listener can fail.

  **The payload gap was settled without touching the pieces contract.** Putting `project` on the discard event was rejected on two recorded grounds: [an event carries what changed](./ARCHITECTURE.md#event-sourcing--discipline) and the project did not change, and [a publisher must not know what its subscribers need](./ARCHITECTURE.md#the-first-consumer-the-idea-catalog-as-a-projection). Instead boards answers its own question — a second projection (`index-pinned-pieces` over `board.piece.*`) maps piece to boards, fed entirely by boards' own events. See [the cross-feature note](./ARCHITECTURE.md#wiring--each-feature-assembles-itself).

  **The subscription is now exact.** `Listener::listens_to` returns *several* subscriptions, so the pin index binds `board.piece.pinned` and `board.piece.unpinned` and nothing else — a move no longer wakes it. That is also what a broker does: a queue carries several bindings, and one matching message still arrives once, which `Listener::hears` is written to guarantee.

  **Still owed:** the projector re-reads the whole board and rewrites the whole set on every pin, where only one piece changed. Applying the delta would be O(1) but order-sensitive, and a version guard cannot rescue it — dropping an out-of-order older delta loses its effect for good, while whole-state writes are safe under "newest wins". So the O(n) buys order-insensitivity, and the honest cost is roughly **double a pin**, since `BoardService::pin` already loads the aggregate. What *is* worth adding when a broker lands: a version on `holds` so two concurrent handlers cannot let an older read overwrite a newer one.

- [ ] **Find-or-start can start two boards for one project.** `BoardService::open` asks the catalog, sees nothing, and starts a board — and those two steps are not atomic. Two opens racing on a project that has no board yet both see an empty listing and both start one. In process the window is narrow; over a broker the projection lags, so two opens in quick succession would reliably do it.

  **It is benign today, and that is not an accident.** The catalog lists boards **ascending by id**, so every reader converges on the same board — the first one started — and the loser is an orphan nobody navigates to. That ordering was chosen so find-or-start would be *settled* rather than picking a different board on different reads; it turns out to be what makes the race survivable too.

  **What would actually fix it:** a uniqueness constraint the store can enforce, which needs a real store. A deterministic board id derived from the project would also work and is deliberately rejected — it forbids the second board that [the model already supports](./ARCHITECTURE.md#ideas-scenes-and-views--the-non-linear-model). **Trigger:** M11, or the first time an orphan board is visible to an author.


- [x] ~~**`app()` knows every feature's internals, and that will not scale.**~~ Resolved with the cheaper move rather than a `Feature` trait: every feature grew a `wiring` crate beside `contract`, `core`, `adapters` and `tests`, and `app()` no longer names a single service, adapter or projector. See [the reasoning](./ARCHITECTURE.md#wiring--each-feature-assembles-itself). **What it did not fix:** the *signature*. Ports still arrive as arguments, so `app()`'s parameter list grows with every feature even though its body no longer does. That needs a registry or a config type, and neither is worth it yet.

- [ ] **A UI component library (thaw).** Considered and deferred, not rejected. Blocked today on versions: `thaw 0.5.0-beta` wants `leptos ^0.8.0` and we are on `0.9.0-beta`. Two reasons to still want a specific justification once that clears, rather than adopting by default: a component library is *all* components, so calling it from builder syntax means `Button(ButtonProps::builder()…)` everywhere — it largely un-decides [the builder choice](./ARCHITECTURE.md#client-conventions); and thaw is Fluent-flavoured, which fights the deliberately bookish palette (Georgia serif, warm paper) that is part of what Weaveling *is*. It also would not help with the hard part, since the prose editor is ProseMirror through interop. **Revisit when** the UI grows tables, date pickers or complex forms — the timeline and codex are where a library starts genuinely paying. The one real gap it would close today (our delete dialog has no focus trap) is answered more cheaply by native `<dialog>` + `showModal()`.

## Deferred until we actually want to deploy

Decided, not forgotten. None of this protects or enables anything today — there is nothing worth shipping yet, so this is work in service of a deployment that does not exist. Pick it up when that changes.

- [ ] **CI** — `cargo fmt --check`, `clippy`, `test`. Two gotchas found the hard way: the client needs its **own** clippy invocation (`--workspace` does not build for `wasm32`, so client lints are silently skipped), and once a Postgres backend exists CI must run **`--all-features`** or feature-gated code is never type-checked.
- [ ] **`ServeDir`** — `services/api` mounts only `/api`, so outside `trunk serve` nothing serves the app. The single-origin design the client depends on (relative `/api/…`, hence no CORS, no build-time host config, no mixed-content trap) is currently true only because Trunk proxies. Needs a `tower_http::services::ServeDir` fallback over `clients/web/dist` with an index fallback. The `fs` feature is already enabled on `tower-http`.
- [ ] **Logging + config** — `TraceLayer` emits at DEBUG while `tracing_subscriber` defaults to INFO, so there is no request log at all; needs a `RUST_LOG` default like `info,tower_http=debug`. And the bind address is hardcoded to `127.0.0.1:3000`; it should come from the environment.

## Open design threads (not yet resolved)

- [ ] **Splitting and joining scenes.** The writing view will want to cut a scene in two at the cursor, and to join a scene onto the one before it. The question is what survives each move. Each scene is [its own CRDT document](./ARCHITECTURE.md#the-scenes-feature), and Yjs cannot transplant items from one document into another. So moving a range of text between scenes is likely delete-plus-insert, and loses the history of the moved text. Decide what an author expects to keep: which half keeps the scene id, and with it the title and the idea links, and where the new scene lands in the outline (presumably right after the old one, in the same section). *Replaces two threads that assumed an idea held its scene, which stopped being true when [ideas and scenes became two pools](./ARCHITECTURE.md#ideas-and-scenes-are-two-pools--decided).*
- [ ] **Does the board keep joining client-side once the pool is too big to fetch whole?** The reasoning is written up under [a board that holds ten thousand ideas](./ROADMAP.md#after-phase-3-sketch-only); the decision is not made. Short version: loading placements per viewport is natural because spots are coordinates, but it buys nothing while the client still fetches every idea in the project to resolve titles. So either both sides get windowed together, or the board's read model carries the title — which denormalises an idea's title into `boards` and needs an `idea.retitled` listener, undoing the [client-side join](./ARCHITECTURE.md#the-board-renders-through-a-frontend-join) we chose on purpose. Worth a conversation before anyone starts, because the cheap-looking change is the one that reshapes the feature.

- [ ] "Present in a scene" vs. "merely mentioned" — do we model both relation types? Belongs to the `cast` view.
- [ ] Time model details: representing parallel scenes + nested time buckets (year ⊃ month ⊃ day). Belongs to the `timeline` view.
- [x] ~~Frontend framework choice within full-stack Rust~~ — Leptos, and the editor spike confirmed it can host ProseMirror without the interop dominating.
- [x] ~~Event versioning/upcasting strategy.~~ Settled: **every event carries its own version**, and upcasting is pure `from -> to` patch functions applied on read, so stored events are never rewritten. Taken from the earlier implementation, which had the design but never exercised it — every real event there sat at version zero. M7 must ship one real patch so ours does not go the same way.
- [ ] **Undo/redo — deferred, not designed.** Decided to leave it off the roadmap entirely for now; event sourcing keeps the option free, so there is no cost to waiting. The question to answer *when* it is picked up: per-aggregate (undo the last thing that happened to this idea or scene) or per-author (undo the last thing *I* did, wherever it happened)? The second is what Ctrl+Z means to an author and needs the agent slot plus a cross-aggregate ordering — meaningfully more work than the first. Events already carry `from`/`to`, so whichever is chosen, the inversion is local.
- [x] ~~**Must a piece have a title?**~~ Settled: normally yes, but the empty string is a legal value — a piece captured on the board starts at `""` and is typed into. `PieceTitle` matches `ProjectName` in every rule except that it permits empty. Untitled is `""` and never `Option<PieceTitle>`, and "Untitled" is something a view draws, never something stored. See [Ideas, scenes and views](./ARCHITECTURE.md#ideas-scenes-and-views--the-non-linear-model).
- [x] ~~**One flat stylesheet, and class names that collide across features.**~~ Settled: every feature partial nests under its own root, `_base`/`_controls`/`_overlays` stay global because sharing is their job, and the rule is written down under [Client conventions](./ARCHITECTURE.md#client-conventions). Two layout assertions now guard it, since the previous three collisions all passed a green suite.

  **The sweep itself bit.** A script that lifted top-level blocks into their root silently dropped `.projects .name { flex: 1 }` — it matched neither the move list nor the keep list, so it vanished, and the workspace rows unpacked while 101 tests stayed green. Caught by looking at the page. If this is ever done again: diff the leaf declarations before and after, which is what found it.
- [x] ~~**`board.rs` is past 500 lines and still growing.**~~ Split. 983 lines in one file became six, none over 350, and the largest function went from **334 lines to 90**.

  | module | holds | lines |
  |---|---|---|
  | `board.rs` | the page and the corkboard's own gestures | 213 |
  | `open_board.rs` | the board, pool and problem; pin/reshape/unpin/retitle | 320 |
  | `card.rs` | the card, its eight grips, the pointer handlers | 206 |
  | `chrome.rs` | action bar, rename editor, zoom controls | 173 |
  | `carrying.rs` | `Carrying`, `Held`, the landing geometry | 344 |
  | `viewport.rs` | the coordinate transform | 227 |
  | `handles.rs` | the state every part of the view shares | 23 |

  **The seam that mattered was `Handles`, not the line count.** It used to be seven signals threaded into every renderer — the "each part adds state every other part can see" complaint. It is now five, and one of them is an `OpenBoard` that owns the data and the only four ways to change it. A reader asking *who can change the board?* has one answer; *what is the author in the middle of?* has another.

  **`carrying.rs` was the real prize.** `Carrying::landing()` — nine handle directions, the minimum size, snapping, the drag threshold — is pure arithmetic that never touches the DOM, and every one of those behaviours used to be reachable only through Playwright. It has **13 native unit tests** now, which run in microseconds. Client unit tests went 10 → 23.

  **One behaviour nuance the split surfaced**, worth knowing: `unpin` used to reach into `selected` to clear it. That coupling is gone, because `chosen()` already looks the piece up among the pinned ones and finds nothing — a stale selection is simply never rendered rather than eagerly cleared. Re-pinning a piece that was selected when it was unpinned will show it selected again, which is the only observable difference.

  Two things deliberately left: `Handles` is still a vague name for what is now "everything a renderer needs", and `corkboard()` at 90 lines is the largest thing left standing.

- [x] ~~**A floating action bar over the selected card.**~~ Built: rename, open, unpin, floating over the selected card, flipping below when the card sits too near the top and stepping aside during a drag. Unpin moved onto it, so the card is a single-column grid holding a title again.

  **One rough edge left, and it is now reachable.** The bar still only flips *vertically*, so a card panned near the right edge pushes it past the board — theoretical when it was written, real since pan landed. The other edge closed itself: the card's height became data when resizing arrived, so the bar computes its own offset and the Rust-constant-versus-CSS drift is gone; `ROOM_ABOVE` is the bar's own height, which is the one thing it is entitled to know.

  Renaming lands in a textarea over the card rather than inside it, which also settles the key-handling worry: the editor stops keydown from reaching the card, so arrows move the caret rather than the card, and there is a test that says so.
- [x] ~~**Cards the author can resize, and what that does to the model.**~~ Built through every layer, in pixels, with `PieceResized` as a sibling of `PieceMoved` and `Reshape` as the one command a gesture issues. See [the write-up](./ROADMAP.md#milestone-9--the-board).

  **Two things it left behind.** A `Reshape` carrying only what changed keeps concurrent writes from clobbering each other, but nothing yet *reads* a card's size except the author who set it — when the live channel lands, a resize in flight and a move in flight on the same card are the first real test of that choice. And the 80×40 floor lives in the client while the domain only refuses zero and negative extents; that split is deliberate (a usable minimum is a drawing decision, having extent at all is an invariant) but it means a hand-rolled request can pin a 1×1 card and the board will accept it.
- [x] ~~**Does moving a card change its z-order?**~~ Yes, and it is recorded: `PieceRaised` alongside `PieceMoved`. See [the write-up](./ROADMAP.md#milestone-9--the-board). Still open, if it ever comes up: a **bring to front** button on the action bar, for raising without moving. The event already exists, so it would need a command and a button and nothing else.
- [x] ~~**A failed request's alarm can be cleared by the next success.**~~ Successes no longer clear it at all; the alarm is dismissible instead. A failure is news, and news does not evaporate because something unrelated worked. The cost is that a successful *retry* leaves the alarm up until dismissed — acceptable, and honest, since something did fail.
- [x] ~~**Only the grip drags, and the title link drags natively.**~~ Settled by making the whole card the handle, which is what a corkboard wants anyway. The grip is gone. The title stays a real `<a>` with a real href — hover shows it, ctrl and middle click still open a new tab — but its plain click is prevented so it selects like the rest of the card, and `draggable="false"` kills Chrome's ghost drag. It is a plain anchor rather than the router's `<A>` on purpose: prevention that depends on which click handler runs first is prevention you cannot reason about.

  **The gesture question settled itself:** a drag on bare board pans, a drag on a card moves it, and cards stop the press from reaching the board, so the two never compete. Pressing bare board also deselects, which means a drag-to-pan lets go of the selected card — deliberate, and there is a test for it. `user-select: none` now sits on the card, which the old grip-only version did not need, because a press used to land on a `<button>` where Chrome will not start a text selection anyway.

- [x] ~~**A live channel for the board.**~~ Promoted out of the TODO and into [M9b](./ROADMAP.md#milestone-9b--the-boards-live-channel), because it is a second live surface with its own architecture rather than a loose end. M9 closed without it: the board is a finished single-author surface, and its other three done-when criteria are met.
- [ ] **Nothing ships the attributions the dependencies require.** The project is **MIT** (`LICENSE`, Benjamin Michel, 2026). Audited at the point the first webfont was chosen: **300 third-party crates and 21 npm packages, no copyleft anywhere.** Crates are `MIT OR Apache-2.0` (155), `MIT` (80), `Unicode-3.0` (18), `Zlib` (5) and similar; npm is 18 MIT and 3 Apache-2.0. The one hit for "LGPL" is `r-efi`, whose licence is `MIT OR Apache-2.0 OR LGPL-2.1-or-later` — a **disjunction**, so taking it under MIT carries no copyleft obligation, and it is a UEFI crate that never compiles for the targets used here.

  So the licences are compatible; what is missing is the other half. MIT and Apache-2.0 both require preserving copyright notices in a distribution, Apache-2.0 additionally wants its licence text and any `NOTICE`, and the OFL wants each font's licence shipped with the font. **The app currently ships none of it** — no attributions page, no third-party licence file. Not urgent while nothing is published; a real gap the moment it is. `cargo-about` or `cargo-deny` can generate the file and keep it honest in CI.

## Parked (decided — don't re-litigate)

- Rust, modular monolith. **No broker** — `libraries/messaging` owns the port, the envelope and an in-process dispatcher; a broker is an adapter for when a second deployable exists. See [Messaging](./ARCHITECTURE.md#messaging--the-seam-now-the-transport-later).
- **PostgreSQL**, settled in [M11](./ROADMAP.md#milestone-11--the-real-store) after being reopened for MongoDB and judged by the conformance suites. One server, one database per feature. Everything above a port was unaffected either way, which is the whole reason the choice could wait that long.
- Two-speed model: ES/CQRS for structure, CRDT (yrs/Yjs) for prose. ES debuted on `pieces` (now `ideas`); ~~projects stay plain CRUD~~ **overturned in [M11a](./ROADMAP.md#step-1--projects-becomes-an-aggregate--done)** — a name carries no history worth sourcing, but a *deletion* does, and carrying two shapes of feature cost more than the aggregate.
- **The tree is a view, not the model.** Ideas and scenes are a pool; `board`, `outline`, `timeline`, `threads` and `cast` each own their own arrangement of them. Position is never a property of an idea or a scene. See [Ideas, scenes and views](./ARCHITECTURE.md#ideas-scenes-and-views--the-non-linear-model).
